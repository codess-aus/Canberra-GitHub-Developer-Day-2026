## Connect the work, not just the tools

The diagram puts GitHub at the centre of a loop. Requests, code changes, product signals and scheduled work arrive from different places. The work then moves through planning, building, deployment and observation, with the result returning as a feature, fix, dependency update, migration, specification, review or deployment.

The important idea is continuity. An agent is more useful when it can work from the signal that started a task, see the relevant repository and team context, and return a result that fits the existing delivery process. A sequence of disconnected prompts makes people rebuild that context at every handoff.

This is a way to think about the product announcements that follow, not a promise that every event or stage is automated by default. Teams choose the tools, permissions and checks that connect their own workflows.
